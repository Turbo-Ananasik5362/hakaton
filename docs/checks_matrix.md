# Матрица проверяемых свойств результата (checks_matrix)

## 1. Введение

**Источники:**
- `oq.json`: `eval/open_queries.json`. В нём общий чек-лист G1–G6, пять запросов с полями `expected` и пункты чек-листов с ключами автопроверки `auto`.
- `oq.md`: `docs/case/open_queries.md`, полный текст чек-листов. Он дословно совпадает с `data/templates/open_queries_checklists.docx` (сверено).
- `case.md`: `docs/case/case.md`, общие требования кейса. Строки, взятые только из него, имеют ID **K\*** и помечены «case.md».
- `findings.md`: `docs/case/findings.md`, найденные подвохи. Строки, взятые только оттуда, имеют ID **F\*** (общие) или **Qn.F\*** (относятся к одному запросу).
- `skill:acr`: навык acr-program-format (структура шаблонов и правила сложения часов). Это вспомогательный источник: из него взяты правила сложения часов и список разделов. Отдельных пунктов по нему не заводилось.

**Нумерация.** G1–G6 и Qn.m повторяют нумерацию источников. Суффиксы a/b/c означают, что один пункт разбит на части: кодовую и смысловую или на несколько кодовых. ID проверок не связаны с ID объектов комплекта (C1, LO1.2, M2, T2.3, L2.1, S4, Q17).

**Колонки:**
- **Свойство** — что именно проверяется, сформулировано так, чтобы результат был однозначным.
- **Источник** — файл и пункт; для `oq.json` в скобках указан ключ `auto`.
- **Проверка** — один из вариантов:
  - `код` — детерминированная проверка;
  - `код+реестр` — сверка с `data/registry/*.json`;
  - `LLM` — смысловая оценка судьёй GigaChat;
  - `код+LLM` — код отбирает кандидатов, LLM решает только спорные случаи;
  - `человек` — автоматически не проверяется.
- **Как проверить** — поля модели, суммы, регэкспы или критерий для судьи. Имена полей предварительные (по плану работ): `HoursRow{total,lk,pr,lb,srs,contact,distance}`, `Topic.lo_ids`, `Competency{knowledge,skills,abilities,tf_codes,lo_ids}`, `TestQuestion{options,key,lo_ids}`, `Seminar{criteria,lo_ids}`, `Lecture{session_no,plan,slides}`, `InterviewQuestion{module_id,lo_ids}`, `FinalAttestation{form,hours,criteria,pass_rule,portfolio_items,example_task,report_requirements,data_requirements,expected_result}`, `Calendar{days[{date,week,hours,topic_ids}]}`, `Source{registry_id|unverified}`, `report.warnings[{type,text}]`, `ClarifyQuestion{param,text}`.
- **Где** — функция-кандидат в `app/core/validate.py`, либо `judge` (общий LLM-судья, критерий J*), либо `eval` (проверка диалога и времени в харнессе, вне validate).
- **Приоритет:**
  - **P0** — пункт G1–G6, пункт открытого чек-листа или обязательное требование кейса; при провале теряются баллы или это блокер.
  - **P1** — смысловая часть пункта, основную часть которого уже закрывает код; подвохи из findings.md; общие требования case.md.
  - **P2** — желательное и «гигиена».

**Принцип для скрытых запросов.** Проверки по запросам нельзя привязывать к номерам Q1–Q5. Их параметры (объём, недели, часов в день, обязательные темы, форма ИА, требуемые слайды) нужно брать из разобранного запроса (`intake`), чтобы те же функции работали на скрытых запросах объёмом от 16 до 500 ч.

### 5.3. Один дешёвый LLM-судья на комплект

**Сколько вызовов:**
- **1 вызов на комплект** после validate.
- **1 маленький вызов на шаге clarify** (только Q4.4b), если были вопросы.

**Что подаётся на вход** — компактная выжимка, а не документ целиком:
- аудитория, объём, форма ИА;
- названия модулей и тем с часами;
- результаты обучения;
- блок ИА;
- названия семинаров и их критерии;
- планы двух случайных лекций;
- кандидаты, отобранные кодом (неизвестные сервисы, пары похожих тем, результаты обучения с низким пересечением с темами).

**Что на выходе** — JSON `{criterion_id: {"pass": bool, "reason": "≤ 25 слов"}}`. Набор критериев выбирается кодом по параметрам запроса, поэтому подходит и для скрытых запросов.

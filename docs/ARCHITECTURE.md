# Архитектура «Каркаса» — агента методиста АЦР

**Статус:** черновик на согласование командой (18.10.2026). Кода по этому документу ещё нет.
**Опирается на:** `docs/case/case.md` (кейс), `docs/case/findings.md` (ловушки образцов и нормативки),
`docs/templates_spec_pk.md` и `docs/templates_spec_dop.md` (устройство двух шаблонов .docx),
`docs/checks_matrix.md` (127 проверяемых свойств результата), `docs/api_contract.md` (временный контракт API).
Решения, принятые по умолчанию и ждущие подтверждения, собраны в разделе 9.

---

## 0. Коротко

1. Один источник правды — pydantic-модель комплекта `Kit` (`app/models.py`). Все объекты имеют стабильные ID,
   связи — только по ID и только в одну сторону (зависимый объект хранит ID того, от чего зависит).
2. **Числа часов не приходят от LLM.** Модель предлагает структуру и относительные веса, `app/core/hours.py`
   раскладывает часы с шагом 0,5 ч ровно в заявленный объём. Суммы по разделам и «Итого» в модели не хранятся —
   они вычисляются, поэтому разойтись не могут.
3. Каждый шаг агента — отдельный навык `app/skills/<step>.md` (промпт GigaChat + имя схемы ответа),
   как в GigaCowork. Один вызов LLM получает только свой кусок каркаса.
4. После каждого этапа — детерминированная самопроверка `app/core/validate.py` (46 проверок V01–V46),
   смысловое — один дешёвый вызов LLM-судьи на комплект.
5. Человек в контуре: содержание генерируется только после утверждения каркаса (или `auto_approve` для автопрогона).
6. Точечная правка идёт по графу зависимостей: пересобирается только то, что зависит от изменённого объекта.
7. Транспорт (API) отделён от ядра: временный контракт сейчас, адаптер под официальный — когда его дадут.
8. **Универсальность.** Никакой подгонки под открытые запросы: ни констант, ни веток «если это запрос 5».
   Всё поведение — из параметров разобранного запроса (`RequestSpec`) и общих правил шаблона; конфликт требований
   решается общим правилом и объясняется методисту. Открытые запросы — только тестовый набор, наравне со стресс-набором.

```
запрос + вложения
      │
  [intake] ──► RequestSpec ──► нехватка параметров? ──да──► [clarify] ──► ответы методиста ─┐
      │                               │нет                                                 │
      ▼                               ▼◄──────────────────────────────────────────────────┘
  разбор референса (код)        [skeleton] ──► SkeletonDraft (веса, без часов)
  ParsedReference                     │
      │                         hours.py (солвер) + calendar ──► validate (часы, структура)
      └── ошибки образца ──►          │
          в предупреждения      КАРКАС ──► утверждение методистом / auto_approve
                                      │
              ┌───────────┬───────────┼────────────┬──────────────┬───────────────┐
        [program_texts] [module_content]×M  [final_attestation]  (литература из реестра — код)
                              │
              ┌───────────────┼───────────────┐
         [lectures]×M    [seminars]×M     [tests]×M (+ вопросы собеседования)
              │
          [slides] (только запрошенные лекции)
                                      │
                       validate ──► точечный добор (1 раунд) ──► [judge]
                                      │
                 render: .docx · .pptx · GIFT · Moodle XML · CSV · kit.json · отчёт
                                      │
                         [patch] ──► граф зависимостей ──► пересборка затронутого
```

## 1. Модель данных (`app/models.py`)

### 1.1. Принципы

- **ID присваивает код, не LLM.** LLM в ответе ссылается на локальные ключи или на ID, которые ей передали;
  код превращает черновик в объекты `Kit` и выдаёт ID. ID латиницей, неизменны в течение жизни комплекта.
- **Отображаемый номер ≠ ID.** «Тема 2.3» в документе — вычисляется из `order` при рендере. При вставке темы
  новые объекты получают следующий свободный ID (`T2.7`), а нумерация в документе пересчитывается.
  В `patch` можно указать и ID, и отображаемый номер — резолвер приводит к ID.
- **Связь хранится один раз**, на стороне зависимого: `Topic.module_id`, `Topic.lo_ids`, `Lecture.topic_ids`,
  `Seminar.topic_id`, `TestQuestion.lo_ids`. Обратные индексы (какие вопросы у LO) строит `app/core/graph.py`.
- **Вычисляемое не хранится:** `HoursRow.total`, `contact`, часы модуля, «Итого», объём программы, номер в документе,
  выдаваемый документ (по типу программы). В JSON-выгрузку они попадают как computed-поля, но при загрузке игнорируются.
- **Черновые модели LLM отдельно от модели комплекта.** Схемы ответов (`*Draft`) не содержат полей часов —
  физически нельзя «протащить» число от модели в документ.
- Все строки для методиста — на русском. Числа — `Decimal` с шагом 0,5.

### 1.2. Схема ID

| Объект | Формат | Пример | Кто создаёт |
|---|---|---|---|
| Компетенция | `C{n}` | `C2` | skeleton |
| Результат обучения | `LO{c}.{n}` | `LO1.2` — 2-й РО компетенции C1 | skeleton |
| Модуль (раздел) | `M{n}` | `M3` | skeleton |
| Тема | `T{m}.{n}` | `T2.3` | skeleton |
| Лекция | `L{m}.{n}` | `L2.1` | lectures |
| Задание семинара/практики | `S{n}` | `S4` | seminars |
| Тест (набор вопросов) | `TS{n}` | `TS1` — итоговый | tests |
| Тестовый вопрос | `Q{n}` | `Q17` | tests |
| Вопрос собеседования (ТК) | `IQ{n}` | `IQ5` | tests (режим interview) |
| Итоговая аттестация | `FA` | `FA` | final_attestation |
| Критерий оценивания | `{owner}.K{n}` | `S4.K2`, `FA.K1` | вместе с владельцем |
| Источник | `SRC{n}` | `SRC3` | код (реестр) |
| День / занятие календаря | `D{n}` | `D12` | код (календарь) |
| Замечание проверки | `{Vxx}-{n}` | `V02-1` | validate |

### 1.3. Сущности

Ниже — поля и смысл. Типы условные (`str`, `list[ID]`, `Decimal`, enum); точные определения — в `app/models.py`.

**ProgramType** — enum: `pk` (ДПП ПК), `pk_internship` (ДПП ПК в форме стажировки), `dop` (дополнительная общеразвивающая).

**Program** (паспорт)

| Поле | Содержимое |
|---|---|
| `type` | `ProgramType` |
| `title` | название без кавычек (кавычки-«ёлочки» ставит рендер) |
| `audience` | `Audience` |
| `form` | `StudyForm`: `ochnaya` / `ochno_zaochnaya` / `zaochnaya` + флаги `eo` (ЭО), `dot` (ДОТ) |
| `total_hours` | заявленный объём (из запроса, не от LLM) |
| `duration` | недели, учебные дни, часов в день (макс.), длина занятия, занятий в неделю |
| `goal`, `tasks` | цель; задачи (для ДОП) |
| `direction`, `level` | только ДОП: направленность (техническая…), уровень (стартовый/базовый/продвинутый) |
| `profstandards` | `list[PSRef]` — только `pk*`: код ПС из реестра; для `dop` всегда пусто |
| `norm_ids` | ID нормативных актов из реестра (`fz273`, `minobrnauki266`, `minpros629`, `minobrnauki816`…) |
| `document` | computed: ПК — «Удостоверение о повышении квалификации установленного образца», ДОП — «Сертификат об освоении программы» |
| `slides_scope` | что требуется на слайды: занятия `[1, 2]` / модуль по ключевому слову / по умолчанию первый модуль с лекциями |

**Audience** — `category` (кто), `age_or_grade` (для школьников: классы/возраст), `entry_level` (входной уровень),
`requirements` (требования к слушателям: СПО/ВО или получающие их — для ПК), `domain` (профессиональная среда: банк, школа…),
`constraints` (например «не требовать программирования»).

**Competency**

| Поле | Содержимое |
|---|---|
| `id` | `C1` |
| `activity` | вид деятельности (колонка «Виды деятельности» в таблице 1.3 ПК) |
| `title` | формулировка компетенции |
| `tf_refs` | `list[TFRef{ps_code, tf_code}]` — **только из реестра**, для `dop` пусто |
| computed | `knowledge` / `skills` / `abilities` — тексты LO этой компетенции по видам (для таблицы 1.3 и 1.5 ДОП) |

**LearningOutcome**

| Поле | Содержимое |
|---|---|
| `id` | `LO1.2` |
| `competency_id` | `C1` |
| `kind` | `know` (знать) / `can` (уметь) / `master` (владеть — «практический опыт» в ПК, «навыки» в ДОП) |
| `text` | формулировка, проверяемая (глагол действия) |
| `tf_code` | необязательно: ТФ из `tf_refs` своей компетенции |

**Module** — `id`, `order`, `title`, `kind` (`regular` / `intro` — вводное занятие ДОП), `control_form`
(форма текущего контроля: «Собеседование», «Контрольная точка № 1 …»), `needs_lectures` (флаг, если на модуль
запрошены слайды — солвер обязан дать ЛК > 0). Часы модуля — computed (сумма тем).

**Topic**

| Поле | Содержимое |
|---|---|
| `id`, `module_id`, `order`, `title` | |
| `lo_ids` | какие РО раскрывает (≥ 1) |
| `hours` | `HoursRow` — заполняет только солвер |
| `content` | `dict[WorkKind, list[str]]` — пункты содержания по видам работы для рабочей программы (2.4); **без чисел часов** |
| `tags` | ключевые слова (для подбора литературы из реестра и проверок обязательных тем) |

**HoursRow** — `lk`, `pr`, `lb`, `srs` (`Decimal`, шаг 0,5, ≥ 0); `distance` — часть контактной работы
(ЛК+ПР+ЛБ), проводимая с ДОТ (0 ≤ distance ≤ contact); computed: `contact = lk + pr + lb`,
`in_person = contact − distance`, `total = lk + pr + lb + srs`. Для ДОП колонки маппятся так:
«Лекции/теория» = `lk`, «Практические» = `pr`, «Самостоятельная работа» = `srs`, `lb = 0`, «Всего аудиторных» = `contact`.

**Lecture** — `id`, `module_id`, `topic_ids`, `session_no` (номер занятия в календаре — для ДОП и запросов
вида «слайды к занятиям 1 и 2»), `title`, `goal`, `plan: list[PlanItem{title, theses[3–5], lo_ids}]`,
`glossary: list[{term, definition}]`, `slides: list[Slide{title, bullets[3–5], notes}] | None` — заполняется
только для лекций из `slides_scope`.

**Seminar** — `id`, `topic_id`, `lo_ids`, `kind` (`practice` / `lab`), `title`, `situation` (ситуация из среды
аудитории), `task`, `steps`, `deliverable` (что сдаёт слушатель), `criteria: list[Criterion{id, text, max_points}]`
(≥ 2), `pass_threshold`. Часы — из `topic.hours.pr/lb` (не хранятся в задании).

**Test** — `id`, `scope` (`final` / `module` + `module_id` / `entry`), `question_ids` (порядок), `pass_threshold`.
**TestQuestion** — `id`, `test_id`, `topic_id`, `lo_ids` (≥ 1), `kind` (`single` / `multiple`), `stem`,
`options` (4), `correct` (индексы), `explanation`, `difficulty` (1–3).

**InterviewQuestion** (текущий контроль-собеседование, в первую очередь стажировка) — `id`, `module_id`, `lo_ids`,
`text`, `answer_points` (что должно прозвучать в ответе), `criteria`.

**FinalAttestation**

| Поле | Содержимое |
|---|---|
| `form` | enum: `project_defense` / `portfolio` / `exam_practical` / `report_defense` / `test` / `zachet` |
| `form_text`, `hours` | формулировка для документа; часы ИА (из запроса или по умолчанию — раздел 3.3) |
| `lo_ids` | какие РО проверяет |
| `requirements` | требования к работе |
| `portfolio_items` | для портфолио: `[{id, title, requirements}]` (ровно столько, сколько в запросе) |
| `example_task` | для экзамена: пример практического задания (среда, «стенд», исходные данные, что сдать) |
| `data_requirements`, `expected_result` | для проекта на данных (в т.ч. «данные обезличены») |
| `report_requirements` | для стажировки: структура отчёта о стажировке |
| `criteria`, `pass_rule`, `procedure` | критерии с баллами, порог «зачтено», регламент защиты |

**Source** — `id`, `kind` (`norm` / `profstandard` / `book` / `doc` / `web` / `software`), `section`
(основная / дополнительная / интернет-ресурсы / ПО), `registry_id | None`, `verification` (`registry` — из реестра,
`catalog` — найдено в каталоге проверенных изданий, `online` — подтверждено онлайн-сверкой, `unverified`),
`authors`, `title`, `year`, `publisher`, `isbn`, `url`, `topic_ids` (необязательно). Библиографическую запись
собирает код из полей (у подтверждённых — из записи каталога, а не из ответа модели); при `unverified` в документе
метка `[не подтверждено]`. Нормативка и ПС тоже попадают сюда, но всегда из реестра.

**Calendar** — `mode` (`sessions` — занятия фиксированной длины, ДОП; `days` — учебные дни с лимитом часов, ПК),
`weeks`, `days_per_week`, `days: list[CalendarDay{id, n, week, hours, items: [{topic_id | "FA", kind, hours}]}]`,
`notes` (например «срок 2 месяца реален только при занятиях без выходных»). Даты не ставятся — «____».

**ProgramTexts** — прозаические разделы: аннотация (1.1 ПК), актуальность (1.1 ДОП), описание формы обучения,
требования к слушателям (текст), МТО, перечень ПО, организация процесса (3.3 ПК), требования к кадрам (3.4),
методические материалы (2.4 ДОП), анализ удовлетворённости (2.5.3 ПК). Пишет навык `program_texts`.

**ValidationReport**

| Поле | Содержимое |
|---|---|
| `status` | `ok` / `warnings` / `errors` |
| `issues` | `list[Issue]` |
| `hours` | сводка по уровням: темы → модули → итог, ИА, контактная/СРС/ДОТ |
| `coverage` | матрица `LO × темы × оценочные средства` |
| `sources` | сколько подтверждено реестром / помечено `[не подтверждено]` |
| `sections` | полнота разделов шаблона |
| `warnings_for_methodist` | `list[{type, text}]`: `reference_errors`, `expectation_gap`, `schedule_tight`, `norm_replaced`, `unverified_sources`, `constraint_conflict` |
| `judge` | результаты LLM-судьи по критериям J1–J9 |
| `cost`, `timing` | ₽, токены и секунды по шагам |

**Issue** — `id` (`V02-1`), `check` (`V02`), `severity` (`error` / `warning` / `info`), `target_ids`,
`message` (для методиста, без жаргона), `detail` (для разработчика), `checklist_refs` (`["G1", "Q5.2"]`),
`fix_by` (`code` / `llm` / `human`), `fixed` (исправлено автодобором).

### 1.4. Модели ввода и черновики LLM

**RequestSpec** (выход intake, после сверки кодом) — `program_type?`, `title?`, `total_hours?`, `audience`,
`form`, `weeks?`, `hours_per_day_max?`, `session_hours?`, `sessions_per_week?`, `fa_form?`, `fa_hours?`,
`required_topics: list[TopicRequirement{label, patterns}]`, `constraints` (`ru_services_only`, `min_practice_share`,
`all_srs`, `no_programming`, `anonymized_data`…), `outputs` (`test_questions`, `slides_scope`),
`reference: ParsedReference | None`, `missing: list[param]`, `assumptions: list[str]`.

**ParsedReference** — результат разбора приложенной программы **кодом** (python-docx / pypdf): тип шаблона,
оглавление, сырые таблицы часов (числа как в документе, включая итоговые строки), найденные коды ПС/ТФ и приказы.
В LLM уходит только оглавление. По сырым числам V45 ищет ошибки образца (запрос 5).

**Черновики** (схемы `response_format`): `IntakeDraft`, `ClarifyDraft`, `SkeletonDraft`, `ModuleContentDraft`,
`LecturesDraft`, `SlidesDraft`, `SeminarsDraft`, `TestsDraft`, `FinalAttestationDraft`, `ProgramTextsDraft`,
`PatchPlanDraft`, `JudgeDraft`. Главное ограничение: в `SkeletonDraft` вместо часов — `weight` (целое 1–10) у модулей
и тем и `mix` (проценты ЛК/ПР/ЛБ/СРС) у темы; ТФ — только ID из переданного списка.

### 1.5. Реестр (`app/core/registry.py`, `data/registry/*.json`)

`norms.json`, `profstandards.json` (есть), `ru_ai_services.json`, `literature.json` (каталог проверенных изданий
и документации по ИТ-направлениям — растёт от прогона к прогону, см. 2.4), `publishers.json` (реальные издательства —
для формальной проверки кандидатов), `tools.json` (официальная документация инструментов с URL и минимальные
поддерживаемые версии — для Q3.6) — создаются при наполнении.
Статус записи `verified` (есть `source_url` и `checked_at`) или `to_verify` (выводится только с меткой).
LLM реестр не пишет и не дополняет; в промпт skeleton передаётся список ТФ кандидатных ПС с их ID.

## 2. Пайплайн и навыки

### 2.1. Состояния сессии

`new` → `need_clarification` → `skeleton_ready` → `generating` → `done`; из любого — `failed` (с отчётом,
что успели). После `done` возможен `patching` → `done`. Состояние и `kit.json` сохраняются после каждого шага в
`data/sessions/<id>/` — после перезапуска сервера генерация продолжается с последнего готового шага
(повторные вызовы LLM бесплатны благодаря кешу).

### 2.2. Формат навыка `app/skills/<step>.md`

Шапка (YAML): `step`, `model`, `max_tokens`, `temperature` (0,2–0,3), `schema` (имя pydantic-класса черновика),
`inputs` (какие поля передаются). Тело на русском: роль → входные данные (`{{placeholder}}`) → правила →
формат ответа. Общие правила, повторяемые во всех навыках:

- не писать числа часов, номера приказов, коды ПС/ТФ — кроме переданных во входе;
- ссылаться только на переданные ID (`LO1.2`, `T2.3`);
- язык и примеры — под аудиторию и её профессиональную среду (`audience.domain`);
- при `ru_services_only` — только сервисы из переданного белого списка;
- не копировать текст референса; брать из него только структуру;
- ответ — только JSON по схеме.

JSON-схема берётся из pydantic-класса и уходит в `response_format: json_schema` (проверено на шлюзе: работает).
Запасной путь — инструкция «верни JSON» + извлечение + до 2 ремонтных попыток с текстом ошибки валидации.

### 2.4. Литература: модель предлагает, код проверяет (`app/core/bibliography.py`)

Задача — дать модели предлагать книги и при этом не выпустить выдуманное издание как настоящее.

1. **Шорт-лист (код).** Из каталога `literature.json` и документации из `tools.json` отбираются до 30 записей,
   подходящих по `tags` тем и названию программы (ключевые слова; при слабом совпадении — эмбеддинги
   `ai-sage/Giga-Embeddings-instruct-3B`, вычисляются для каталога заранее и кешируются).
2. **Навык `literature` (1 вызов).** Модель выбирает из шорт-листа по ID (основная / дополнительная литература,
   интернет-ресурсы) и может предложить до 6 новых кандидатов — **только структурой** (авторы, название, год,
   издательство, ISBN если знает, URL). Готовую библиографическую строку модель не пишет — её собирает код.
3. **Проверка каждого кандидата (код), по порядку:**
   - **каталог:** нечёткое совпадение нормализованных названия и фамилии автора с записью `literature.json` →
     берутся выходные данные из каталога (не модельные), `verification = catalog`;
   - **формальные признаки:** контрольная сумма ISBN-10/13 (если ISBN указан); год не позже текущего и не слишком
     старый для ИТ-темы (порог в настройках); издательство из `publishers.json`; URL — домен официальной
     документации из `tools.json` или реестра;
   - **онлайн-сверка (опция, по умолчанию выключена):** поиск по ISBN или названию в открытом библиографическом
     каталоге. Включается, только если на ВМ есть интернет и это разрешено правилами (вопрос организаторам, раздел 9).
     Это не LLM-сервис, а обычный поиск по каталогу.
4. **Решение:**
   - подтверждён (реестр, каталог, онлайн) → в список как есть;
   - формальные признаки в порядке, но подтвердить не удалось → в список с меткой `[не подтверждено]`,
     не больше 2 на подраздел;
   - формальные признаки провалены (битый ISBN, год из будущего, неизвестное издательство) → **кандидат отбрасывается**,
     в отчёт — «модель предложила источник, который не удалось подтвердить, он не включён».
   - Если в подразделе осталось меньше минимума — пометка `[заполнить методисту]`.
5. **Обратная связь:** все неподтверждённые и отброшенные кандидаты пишутся в `logs/unverified_sources.jsonl`.
   При разработке их сверяют с первоисточниками и пополняют `literature.json` — каталог растёт с каждым прогоном,
   и доля `[не подтверждено]` падает.

Нормативные акты, профстандарты и коды ТФ модель не предлагает никогда — только реестр (раздел 1.5).

## 3. Солвер часов (`app/core/hours.py`)

### 3.1. Вход и выход

**Вход:**
- структура из `SkeletonDraft`: модули `{key, weight}`, темы `{module_key, weight, mix{lk, pr, lb, srs}}`;
- жёсткие ограничения из `RequestSpec` и правил шаблона: `total_hours`, `fa_hours`, `program_type`,
  `min_practice_share`, `all_srs`, `session_hours`, `sessions_per_week`, `weeks`, `hours_per_day_max`, `dot`
  (+ доля ДОТ), модули с `needs_lectures`, минимумы (тема ≥ 1 ч, модуль ≥ 2 ч; для занятий фиксированной длины —
  тема кратна длине занятия, если тем не больше, чем занятий);
- зафиксированные методистом строки (`locked`) — для ручной правки и patch.

**Выход:** `HoursRow` каждой темы, часы ИА, `Calendar`, `SolverLog` (что и почему скорректировано),
`list[ConstraintConflict]`. Инвариант: `Σ темы + ИА = total_hours` **точно**, все значения кратны 0,5.

### 3.2. Алгоритм

Работаем в целых «получасах» (`u = 0,5 ч`), чтобы не было ошибок округления.

1. **ИА.** `B = total − fa_hours`. Часы ИА: из запроса; иначе по умолчанию `pk` и `pk_internship` — 2 ч;
   `dop` — одно занятие (`session_hours`), если программа из занятий фиксированной длины, иначе 2 ч.
2. **Модули.** Метод наибольших остатков (Гамильтон) по `weight` с минимумом на модуль: сначала каждому выдаётся
   минимум, остаток делится пропорционально весам, дробные остатки раздаются по убыванию.
3. **Темы внутри модуля** — тем же методом по `weight` темы, сумма = часы модуля. Для занятий фиксированной длины
   делятся не получасы, а занятия (единица = `session_hours`).
4. **Виды работы внутри темы** — тем же методом по `mix`, после применения правил типа (3.3).
5. **Глобальные поправки** (жадно, по полчаса, не меняя суммы тем):
   - доля практики: пока `Σ pr < min_practice_share × total`, переносить `u` из `lk` (затем из `srs`) в `pr`
     в теме с наибольшим дефицитом относительно её `mix`;
   - `needs_lectures`: в каждой теме такого модуля `lk ≥ 1 ч` (перенос из `pr`/`srs`);
   - ДОТ: `distance` раздаётся Гамильтоном по контактным часам с приоритетом ЛК, затем ПР.
6. **Проверка** всех ограничений (V01–V11 на результате). Нарушение, которое нельзя устранить перераспределением, —
   `ConstraintConflict` с понятным текстом. Солвер **не нарушает ограничения молча**: конфликт уходит в отчёт
   или в уточняющий вопрос.

Сложность линейная, внешних солверов нет. Детерминизм: при равных остатках — порядок по `order`.

### 3.3. Правила по типам программ

| Тип / условие | Правило |
|---|---|
| `pk` | `total = lk + pr + lb + srs` по строке; ЛБ только если skeleton предложил лабораторные |
| `pk_internship` или `all_srs` | `lk = pr = lb = 0` во **всех** строках, включая «Итого»; всё в СРС; текущий контроль — внутри СРС тем, отдельной строки с часами нет |
| `dop` без самостоятельной работы (только очные занятия) | `srs = 0`; ИА — на последнем занятии внутри объёма |
| `dop` | «Всего аудиторных» = `lk + pr`; «Общая» = аудиторные + СР; ИА отдельной строкой |
| очно-заочная с ДОТ | `distance > 0` и `in_person > 0` в сумме; разбивка видна в документе |

### 3.4. Календарь

- **Режим `sessions`** (ДОП, «занятия по 2 часа два раза в неделю»): `N = (total) / session_hours` занятий,
  `sessions_per_week` в неделю, недель `= ceil(N / sessions_per_week)` и ≤ `weeks`. Темы раскладываются по занятиям
  по порядку; занятие может содержать части двух тем; ИА — последнее занятие.
- **Режим `days`** (ПК): упаковка тем по порядку в учебные дни ёмкостью `hours_per_day_max`
  (по умолчанию 6 ч для ПК, 4 ч для стажировки, если в запросе не задано).
- **Общее правило «срок против нагрузки»** (одинаково для любого запроса):
  - **жёсткие** ограничения — объём, лимит часов в день, длина занятия, занятий в неделю (если заданы);
    они не нарушаются никогда;
  - **мягкое** — желаемый срок («4 недели», «около двух месяцев», «примерно месяц»);
  - число учебных дней `N` даёт упаковка; дней в неделю `d` — минимальное из `5…max_days_per_week`
    (по умолчанию 6, настраивается), при котором `ceil(N / d)` недель укладывается в желаемый срок
    с допуском ±15 %;
  - если такого `d` нет — берётся `d = max_days_per_week`, и в отчёт идёт предупреждение `schedule_tight` с цифрами:
    сколько недель реально нужно, какая нагрузка в день нужна для желаемого срока, сколько учебных дней получается;
  - в программу (1.8 / 1.4 и календарный график) пишется **расчётный** срок по календарю, а не желаемый из запроса.
  Пример: 256 ч, ≤ 4 ч/день, «около двух месяцев» → 64 учебных дня, при 6 днях в неделю — 11 недель;
  в отчёте: «в 2 месяца при нагрузке до 4 ч в день программа не укладывается: нужно 11 недель при шестидневке
  или около 5 ч в день».
- Календарь детерминирован и пересчитывается при любом изменении часов (дёшево, без LLM).

### 3.5. Ручная правка часов (`rebalance`)

Методист в редакторе каркаса меняет часы строки → строка становится `locked` → солвер перераспределяет остальное
**в пределах того же модуля** (если модуль тоже зафиксирован — в пределах программы) так, чтобы сумма снова была
ровно равна объёму. Если зафиксировано больше объёма — конфликт показывается сразу, до утверждения.

### 3.6. Тест-сценарии (обязательные)

16 ч ДОП = 8 × 2 ч, практика ≥ 8 ч, СР = 0, ИА на 8-м занятии · 24 ч как в образце интенсива (структура совпадает) ·
36 ч ПК очно-заочно с ДОТ · 72 ч ПК на 4 недели · 256 ч стажировка (254 СРС + 2 ИА, нули везде) · 500 ч ·
модуль со слайдами получает ЛК · конфликт «все-СРС + доля практики 50 %» даёт `ConstraintConflict` ·
свойство: для случайных весов сумма всегда точна, все значения кратны 0,5, нет отрицательных.

## 5. Граф зависимостей и точечная пересборка (`app/core/graph.py`, `app/pipeline/patch.py`)

### 5.1. Рёбра (зависимый → от чего зависит)

```
LO ─► Competency                      Topic ─► Module, LO*
Lecture ─► Topic*, Module             Slide ⊂ Lecture
Seminar ─► Topic, LO*                 TestQuestion ─► Topic, LO*, Test
InterviewQuestion ─► Module, LO*      FA ─► LO*
Source ─► Topic* (необязательно)      Topic.hours ─► солвер(модуль, ограничения)
Calendar ─► все Topic.hours, FA.hours ProgramTexts ─► Program, названия модулей
Рендеры и отчёт ─► всё (пересобираются всегда — это дёшево, без LLM)
```

### 5.2. Что пересобирается

| Операция | Пересобирается LLM | Пересчитывается кодом | Не трогается |
|---|---|---|---|
| Заменить тему `T2.3` (название/содержание) | содержание `T2.3`; лекции, где `T2.3 ∈ topic_ids` (и их слайды, если были); задания с `topic_id = T2.3`; вопросы с `topic_id = T2.3` (то же число, те же РО); вопросы собеседования модуля M2, если касались темы | литература по новым `tags`; календарь (только подписи); рендеры; validate | всё остальное, включая часы (ID `T2.3` сохраняется, часы остаются, если правка о них не просит) |
| … и у темы сменились РО | + оценочные средства для РО, у которых после правки стало < 2 средств | матрица покрытия | остальные РО |
| Изменить часы темы/модуля | только если у темы появился/исчез вид работы: появилась ПР → задание; появилась ЛК → лекция; исчезла → объект архивируется | солвер `rebalance` в пределах модуля; календарь | содержание тем без смены видов работы |
| Усложнить тест `TS1` (или вопросы `Q…`) | вопросы этого теста: `difficulty + 1`, те же ID, РО и распределение по темам | GIFT/XML/CSV; validate V18 | всё остальное |
| Заменить РО `LO1.2` | темы с `LO1.2` — содержание (по решению patch-плана); все средства с `LO1.2` | таблица компетенций | прочие РО и их средства |
| Изменить аудиторию / объём («адаптация», сверх плана) | фактически новый каркас; переиспользуются темы, которые остались | солвер целиком | — |

### 5.3. Алгоритм patch

1. `patch`-навык превращает инструкцию в типизированный план: `{operation, target_ids, params}`
   (`replace_topic`, `change_hours`, `harden_test`, `replace_lo`, `add_topic`, `remove_topic`, `regenerate`).
   Цель задаётся ID или отображаемым номером («тема 2.3»).
2. `graph.affected(plan)` — замыкание по обратным рёбрам с учётом семантики операции (таблица 5.2).
3. Генерация только для затронутых объектов теми же навыками, что при сборке, с инструкцией методиста в контексте.
4. Солвер (если менялись часы) → календарь → validate → рендер.
5. В ответе: `changed_ids`, новый отчёт, `revision + 1`; запись в `history` (для отката).

**Инварианты (проверяются тестами E04):** объекты вне `changed_ids` побайтно совпадают
(сравнение хешей `model_dump_json` каждого объекта); суммы часов сходятся; ID не переиспользуются.

## 6. API и интерфейс (`app/api/`, `app/web/`)

### 6.1. Слои

```
app/api/routes_v1.py      временный контракт (docs/api_contract.md) — оставляем и после официального
app/api/adapters/official.py  официальный формат автопрогона: преобразует запрос → RequestInput, Kit → ответ
app/api/schemas.py        транспортные DTO (не путать с app/models.py)
app/pipeline/orchestrator.py  машина состояний сессии, вызовы шагов, параллельность
app/storage/sessions.py   data/sessions/<id>/: state.json, kit.json, files/, log.jsonl
```

Ядро (`app/core`, `app/pipeline`) не знает о HTTP; адаптеры — тонкие функции «формат ↔ RequestInput / Kit».

### 6.2. Эндпоинты (временный контракт)

`POST /api/v1/sessions` · `POST /api/v1/sessions/{id}/answers` · `POST /api/v1/sessions/{id}/approve` ·
`POST /api/v1/sessions/{id}/patch` · `GET /api/v1/sessions/{id}` · `GET /api/v1/sessions/{id}/files/{name}` ·
`POST /api/v1/run` · `GET /health`. Плюс служебный `POST /api/v1/hours/rebalance` для редактора каркаса.

Генерация комплекта длится минуты, поэтому два режима:
- **синхронный** (`/run`, `approve` с `?wait=true`) — ответ, когда всё готово; для скриптов и, возможно, автопрогона;
- **асинхронный** (по умолчанию для интерфейса) — `approve` сразу возвращает `status: generating` и прогресс по шагам,
  клиент опрашивает `GET /sessions/{id}` раз в 2 с (стриминга у шлюза нет, поэтому прогресс — по шагам).

Ошибки — JSON с понятным текстом, без 500 на плохом вводе. `auto_approve: true` — каркас утверждается сразу,
но уточняющие вопросы всё равно задаются, если данных не хватает.

### 6.3. Адаптер официального контракта

Когда организаторы пришлют формат: вставить его в `docs/api_contract.md`, написать `adapters/official.py`
и тест на пример запроса/ответа. Неизвестные заранее вопросы, которые решает адаптер: передаёт ли харнесс ответы
на уточнения (второй вызов или поле `answers` сразу), ждёт ли синхронного ответа, в каком виде ждёт файлы
(URL или base64). Пока не знаем — поддерживаем оба варианта: и `need_clarification`, и приём `answers` сразу.

### 6.4. Ресурсы ВМ (2 ядра, 4 ГБ)

Один процесс uvicorn, asyncio. Одновременно генерируется не больше 2 сессий (очередь, ответ `queued` для третьей);
не больше 6 одновременных вызовов LLM на процесс (семафор 4 на сессию). python-docx и python-pptx лёгкие;
тяжёлых зависимостей нет. Кеш LLM (`cache/llm/`) и сессии (`data/sessions/`) не удаляются при выкладке —
повторный автопрогон тех же запросов при неизменных промптах бесплатен.

### 6.5. Веб-интерфейс

FastAPI + Jinja2 + немного vanilla JS, без сборщиков, на русском, для методиста без ИТ-фона:
1. запрос + загрузка .docx/.pdf/.txt;
2. уточняющие вопросы с вариантами ответа;
3. редактор каркаса: цель, компетенции и РО, таблица учебного плана; при правке часов сразу видно, сходится ли сумма
   (`rebalance`), кнопка «Утвердить»;
4. прогресс генерации по шагам;
5. отчёт самопроверки — статусы цветом **и** текстом, предупреждения методисту отдельным блоком;
6. скачивание .docx / .pptx / GIFT / Moodle XML / CSV / JSON;
7. поле точечной правки («замени тему 2.3 на …», «усложни итоговый тест»).

## 7. Бюджет и скорость

### 7.1. Исходные данные (замер на шлюзе 18.10.2026)

  Ниже принято **40 ток/с** — оценки времени пересчитать после замера.
- Расчёт консервативный: кешированные шлюзом токены считаем по полной цене.

### 7.5. Политика экономии

1. **Кеш на диске** (`cache/llm/<sha256>.json`): повтор того же запроса при тех же промптах — 0 ₽.
2. **Предохранитель** `LLM_DAILY_BUDGET_RUB` (по умолчанию 90): перед генерацией комплекта код оценивает стоимость
   по размеру каркаса. Если `остаток < оценка × 1,5` — экономный режим; если не хватает и на него —
   комплект собирается из того, что успели, а недостающее помечается `[заполнить методисту]` (лучше неполный
   комплект с честным отчётом, чем пустой ответ).
3. **Ограничение детализации** для больших программ: число модулей и тем, пункты содержания 3–5 на вид работы,
   слайды только для `slides_scope`.
4. **Правило для разработки:** суточный лимит 100 ₽ общий для всей команды, ноутбуков и ВМ, а автопрогон идёт
   в 06:00–10:00. Если сутки считаются с 00:00 МСК, то **любые live-прогоны после полуночи съедают бюджет утреннего
   автопрогона**. Live для отладки — только с 10:00 до 23:59; ночью — `mock` / `replay`.
   `scripts/budget.py` видит только свой ноутбук — траты коллег и ВМ в нём не видны.

### 7.6. Параллельность и время комплекта 72 ч

- После утверждения каркаса параллельно стартуют: `program_texts`, `final_attestation`, `literature`, `module_content` × M.
- Для каждого модуля, как только готово его содержание: `lectures`, `seminars`, `tests` (параллельно),
  затем `slides` для лекций из `slides_scope`. Глубина цепочки — 3 вызова.
- Семафор 4 вызова на сессию. 29 вызовов по ≈ 25–40 с → ≈ 8 волн → **≈ 5 мин**, плюс judge ≈ 20 с, автодобор ≈ 1 мин,
  рендер ≈ 10 с → **≈ 6–7 мин** при лимите 20 мин. Запас покрывает скорость генерации до ≈ 15 ток/с.
- Если замер покажет < 30 ток/с, skeleton делится на два шага: (а) компетенции, РО, список модулей;
  (б) темы каждого модуля — параллельно. Это держит каркас в пределах 3 минут.
- Ретраи на 429/5xx с экспоненциальной паузой; таймаут вызова 120 с; ответ с `finish_reason = length` —
  повтор с разбивкой (меньше тем на вызов), а не ремонт обрезанного JSON.

| Рендер .docx по шаблону сложнее, чем кажется (объединения, альбомные секции, списки) | средняя | спецификации шаблонов уже есть; ПК — на копии образца с очищенным телом, ДОП — на чистом документе со своими стилями |
| Скрытые запросы не похожи на открытые (500 ч, ДОП для взрослых, ПК без подходящего ПС) | средняя | проверки параметризованы `RequestSpec`; стресс-набор из 20 запросов в mock |
| Приказ № 499 против № 266 оценят «по ТЗ» | средняя | ссылаемся на № 266, в отчёте поясняем замену; вопрос организаторам |
| Конфликты в общем репозитории | средняя | зоны ответственности по файлам (раздел 10), `fetch` + `rebase` перед push, без force-push |
| Копирование текста референса | низкая | в LLM уходит только оглавление; проверка V42 по шинглам |
| Модель предлагает выдуманные книги | высокая / потеря доверия к комплекту | схема 2.4: выбор из каталога по ID, кандидаты только структурой, формальные проверки (ISBN, год, издательство), отброс провалившихся, метка для остальных, пополнение каталога по логу кандидатов |
| Подгонка под открытые запросы в ущерб скрытым | средняя | принцип 8 раздела 0; стресс-набор из 20 разнообразных запросов в mock наравне с открытыми |

**Нельзя резать** (обязательно по кейсу): оба шаблона и любой объём; приём .docx/.pdf/текста и уточнения; карта
компетенций со связями; УП и УТП с проверкой сумм; тесты с ключами и привязкой к РО; задания семинаров с критериями;
планы лекций и .pptx хотя бы для одного модуля; .docx по шаблону.

**Режем первым → последним:**
1. режимы «актуализация» и «адаптация» (сверх плана);
2. красота веб-интерфейса (оставить формы и таблицы);
3. Moodle XML и CSV (оставить GIFT);
4. LLM-судья (оставить только кодовые проверки и предупреждения);
5. точечная правка свободным текстом (оставить «пересобрать объект по ID»);
6. полный режим генерации (оставить только экономный `module_pack`);
7. рассуждающая модель — уже не используется по умолчанию.

## 10. Раскладка кода и зоны ответственности

```
app/
  models.py              Kit и все сущности (контракт для всех; правки — только по согласованию)
  config.py              настройки, загрузка .env, пути
  llm.py                 клиент шлюза: mock/live/replay, кеш, учёт расхода, предохранитель, json_schema + ремонт
  core/
    ids.py               выдача ID, резолвер «тема 2.3» → T2.3
    hours.py             солвер часов и rebalance
    calendar.py          календарь (sessions / days)
    validate.py          V01–V46, сбор ValidationReport
    registry.py          загрузка реестра, поиск ПС/ТФ/норм/сервисов/литературы
    reference.py         разбор приложенной программы в ParsedReference
    copycheck.py         шинглы для V42
    bibliography.py      шорт-лист каталога, проверка кандидатов литературы, сборка библиографических записей
    graph.py             обратные индексы и affected() для patch
  pipeline/
    orchestrator.py      машина состояний, параллельность, бюджет
    intake.py clarify.py skeleton.py content.py patch.py judge.py report.py
  skills/                intake.md clarify.md skeleton.md program_texts.md module_content.md lectures.md
                         slides.md seminars.md tests.md final_attestation.md literature.md patch.md judge.md
  render/
    tables.py            ProgramTables — снимок таблиц для рендеров и V31
    docx_pk.py docx_dop.py pptx.py gift.py moodle_xml.py csv_tests.py kit_json.py report_docx.py
  api/                   routes_v1.py schemas.py adapters/official.py
  storage/sessions.py
  web/                   templates/ static/
tests/                   по файлу на модуль ядра; fixtures/llm/<step>/ для mock; fixtures/kits/ (вкл. образец 248 ч с ошибками)
```

Порядок работ: `models.py` → параллельно `hours.py` + `calendar.py`, `validate.py`, `registry.py` + `reference.py`,
`llm.py` → intake/clarify/skeleton + API → первый деплой со сквозным сценарием до каркаса → содержание → рендеры →
отчёт и patch → интерфейс. Сейчас код пишет один человек; если подключатся ещё участники, зоны делятся по директориям
`core/`, `pipeline/`+`skills/`, `render/`, `api/`+`web/`, а `models.py` меняется только по согласованию,
потому что от него зависят все.

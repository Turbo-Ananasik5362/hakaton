# Каркас — ИИ-агент методиста

Агент получает свободный запрос методиста («нужна программа повышения квалификации на 72 часа для…»)
и собирает образовательную программу по одному из двух шаблонов Академии цифрового развития:
дополнительная профессиональная программа повышения квалификации или общеразвивающая программа.
К программе он готовит комплект материалов: учебный и учебно-тематический планы, календарный график,
рабочую программу модулей, лекции, задания семинаров, тесты, итоговую аттестацию, литературу и слайды.
Затем агент сам проверяет комплект (часы, связи результатов обучения с темами и заданиями, нормативные
ссылки, копирование образцов) и пишет отчёт для методиста.

## Быстрый старт (3 команды, без ключей)

Нужен Python 3.10 или новее. Команды выполняются в корне репозитория (Linux и macOS; в Windows вместо
`.venv/bin/` пишите `.venv\Scripts\`).

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/uvicorn app.main:app --port 8000
```

Без ключей шлюза сервер работает в режиме **mock**: вместо GigaChat отвечают заготовленные ответы из
`tests/fixtures/llm/`, сеть не нужна и деньги не тратятся. В логе и в `GET /` выводится предупреждение,
что ответы модели не настоящие.

Проверка, что сервер жив:

```bash
curl -s http://127.0.0.1:8000/health
# {"status":"ok","llm_mode":"mock","llm_ready":false,"version":"0.5.0+<коммит>"}
```

Интерактивная документация API: http://127.0.0.1:8000/docs.

## Работа с настоящей моделью (live)

1. Скопируйте `.env.example` в `.env` (в корне проекта) и заполните две переменные:
   - `OPENAI_BASE_URL` — адрес OpenAI-совместимого шлюза с моделями GigaChat;
   - `OPENAI_API_KEY` — ключ доступа к шлюзу.

   Вместо файла можно задать те же переменные в окружении: окружение важнее файла.
2. Перезапустите сервер. При `LLM_MODE=auto` (по умолчанию) он сам перейдёт в режим `live`.
   Проверка: `GET /health` → `"llm_mode": "live", "llm_ready": true`. Значение ключа сервер никогда не показывает.

Остальные переменные (модель, суточный лимит расходов, параллельность, таймауты) описаны в `.env.example`.

> Если в `.env` лежат ключи, локальный `uvicorn` по умолчанию работает с настоящей моделью и тратит общий
> суточный бюджет. Для разработки без расходов добавьте в `.env` строку `LLM_MODE=mock`.

### Режимы `LLM_MODE`

| Режим | Что делает | Когда |
|---|---|---|
| `auto` (по умолчанию) | `live`, если заданы `OPENAI_BASE_URL` и `OPENAI_API_KEY`, иначе `mock` с предупреждением | всегда, если нет особых причин |
| `live` | только настоящий шлюз; без ключей вызовы модели завершаются ошибкой | сервер, который обязан работать с моделью |
| `mock` | заготовленные ответы из `tests/fixtures/llm/`, без сети и расходов | разработка, демонстрация без ключей, тесты |
| `replay` | только ответы из кеша `cache/llm/` (промах кеша — ошибка), без расходов | повтор уже сделанного живого прогона |

Все живые ответы кешируются в `cache/llm/`: повторный такой же запрос бесплатен. Расход по каждому вызову
пишется в `logs/llm_cost.jsonl`.

## Пример: программа по одному запросу

`POST /api/v1/run` выполняет весь путь за один синхронный вызов: разбор запроса, каркас, автоматическое
утверждение каркаса, генерация содержания, самопроверка. Если данных не хватает, вместо комплекта
придут уточняющие вопросы (`status: need_clarification`); ответы передаются в поле `answers` того же запроса.

```bash
curl -s -X POST http://127.0.0.1:8000/api/v1/run \
  -H 'Content-Type: application/json' \
  -d '{"request": "Нужна дополнительная общеразвивающая программа «Первые шаги в Python» для школьников 8 и 9 классов без опыта программирования. Объем 16 часов, занятия очно по 2 часа два раза в неделю. Практики должно быть не меньше половины всех часов. В конце каждый ученик защищает небольшой проект, например простую игру или чат-бота. Нужны итоговый тест на 10 вопросов и слайды для первых двух занятий."}' \
  -o result.json
```

В `result.json`:
- `status` — `done`, если комплект готов;
- `kit` — весь комплект в JSON (структура — `app/models.py`);
- `report` — отчёт самопроверки: замечания с указанием, где и что не так, стоимость и время по шагам;
- `message` — итог автопроверки человеческим языком (например, «Комплект собран, ошибок нет, 1 предупреждение»);
- `files` — ссылки для скачивания, например
  `curl -s -O http://127.0.0.1:8000/api/v1/sessions/<session_id>/files/kit.json`.

Файлы каждой сессии лежат на диске в `data/sessions/<session_id>/files/`:
- `program.docx` — программа по шаблону АЦР;
- `slides.pptx` — слайды к лекциям, которые просили в запросе (титул, слайд на пункт плана, итоги, заметки докладчика);
- `tests.gift`, `tests_moodle.xml` — тесты для импорта в Moodle (категории по модулям, пояснения к ответам);
- `tests.csv` — те же вопросы таблицей (Excel, разделитель «;»);
- `report.md` — отчёт автопроверки для методиста: итог одной фразой, что исправить и как, часы, покрытие
  результатов обучения, источники, совпадение с образцом, смысловая проверка, что пропущено, стоимость и время
  (тот же отчёт — последним приложением в `program.docx`);
- `kit.json`, `report.json` — комплект и отчёт самопроверки.

Приложенные к запросу документы — в `data/sessions/<session_id>/inputs/`. Каждый выданный файл агент после записи
перечитывает и сверяет с комплектом (проверка V31 в отчёте). Если для файла нет материала (например, в стажировке нет лекций и тестов),
его нет в `files`, а причина — в `notes`. Примеры по открытым запросам — `eval/samples/q1…q5/`
(пересобрать: `.venv/bin/python scripts/render_samples.py`). Шапка организации на титульном листе (название,
ОГРН/ИНН/КПП, адрес, город) берётся из `data/organization.json`.

Вложения (образец программы `.docx`, `.pdf` или `.txt`) передаются в поле `attachments`:
`[{"filename": "образец.docx", "content_base64": "..."}]`.

### Пошаговый режим с утверждением каркаса

Для работы методиста предназначен пошаговый путь, где человек утверждает каркас до генерации содержания:

1. `POST /api/v1/sessions` с `{"request": "..."}` → уточняющие вопросы или готовый каркас (`skeleton_ready`):
   цель, компетенции, результаты обучения, модули и темы с часами;
2. `POST /api/v1/sessions/{id}/answers` → ответы на вопросы;
3. `POST /api/v1/sessions/{id}/approve` → утверждение каркаса (можно с правками) и запуск генерации;
4. `GET /api/v1/sessions/{id}` → ход генерации и готовый комплект;
5. `POST /api/v1/sessions/{id}/patch` → точечная правка одного объекта, например темы `T2.3`
   (в этой версии ещё не подключена: отвечает понятным сообщением `step_unavailable`).

Полное описание запросов, состояний и ошибок — `docs/api_contract.md`.

## Ограничения, которые соблюдает агент

- **Только шлюз GigaChat.** Код обращается к модели только по адресу из `OPENAI_BASE_URL` и только к моделям
  GigaChat. Других внешних сервисов агент не вызывает.
- **Бюджет.** Суточный предохранитель `LLM_DAILY_BUDGET_RUB`: после лимита живые вызовы отклоняются с понятной
  ошибкой. Перед генерацией агент оценивает стоимость и при нехватке денег переходит в экономный режим.
  Ориентир: комплект на 72 часа — около 11 ₽ и 3–5 минут.
- **Человек в контуре.** Содержание генерируется только после утверждения каркаса методистом
  (`/approve`). Для автоматической проверки есть `/api/v1/run` и флаг `auto_approve`.
- **Часы считает код, а не модель.** Модель предлагает структуру и относительные веса, солвер раскладывает часы
  с шагом 0,5 ч ровно в заявленный объём. Числа часов из ответов модели в документ не попадают.
- **Нормативка и литература — из реестра.** Профстандарты, коды трудовых функций, приказы, книги и документация
  берутся из `data/registry/*.json`, где у каждой записи есть ссылка на источник. Всё, чего нет в реестре,
  помечается «[не подтверждено]».
- **Реквизиты пустые.** Номер и дата приказа, ФИО преподавателей и подписи остаются полями `____`.
- **Без копирования образцов.** Совпадения с приложенным образцом проверяются по шинглам.

## Надёжность

- **Сбои шлюза.** Клиент повторяет вызов при 429, 5xx, обрыве и таймауте: при 429 («шлюз перегружен запросами
  команды») — с паузами 5–30 с, суммарно не дольше 3 мин; при сбоях сервера — до `LLM_MAX_RETRIES` раз.
  Одновременно идёт не больше `LLM_CONCURRENCY` вызовов на весь сервер.
- **Повтор шагов.** Шаг генерации, после которого нет результата, повторяется один раз отдельной волной. Не помогло —
  шаг пропущен, комплект собирается из готового, недостающее помечено «[заполнить методисту]», причина — в `notes`.
  Если в волне не прошёл ни один вызов, а шлюз не отвечал (не путать с 429 — перегрузкой), дальше вызовы модели
  в этой сессии не запускаются (кроме одного повтора): комплект собирается из готового, а не после минут повторов.
- **Ответы модели.** Ответ проверяется по JSON-схеме; при ошибке — до двух ремонтных попыток с текстом ошибки,
  обрезанный ответ дробится на части, длинный список — компактный повтор.
- **Бюджет.** Суточный предохранитель `LLM_DAILY_BUDGET_RUB`; перед генерацией агент оценивает стоимость и при нехватке
  денег выбирает экономный режим (один вызов на модуль).
- **Дедлайн.** На генерацию одной сессии — не больше `GENERATION_DEADLINE_S` (25 мин): оставшиеся вызовы модели
  пропускаются, сборка, выгрузки и самопроверка выполняются, в `notes` — что не успели.
- **Перезапуск сервера.** Состояние и комплект сохраняются после каждого шага; после перезапуска незавершённые сессии
  (моложе 2 ч) продолжаются с последнего готового шага, повторные вызовы модели берутся из кеша.
- **Нагрузка.** Не больше `RATE_LIMIT_PER_MINUTE` (30) новых сессий в минуту с одного адреса и
  `MAX_ACTIVE_SESSIONS` (50) сессий в работе; генерируются одновременно 2, остальные ждут в очереди. Сверх лимита —
  ответ 429 с понятным текстом и заголовком `Retry-After`.
- **Ошибки.** Каждая ошибка шага получает код и подсказку методисту: временная (повторить позже), бюджет, ответ
  модели, настройка шлюза, дедлайн, ошибка программы (трассировка — в журнале сессии `data/sessions/<id>/log.jsonl`).
  Сбой одной выгрузки не мешает остальным; комплект в JSON выдаётся всегда.

## Архитектура

```
запрос ─► intake (разбор) ─► clarify (вопросы) ─► skeleton (каркас: цель, компетенции, модули, веса)
        ─► солвер часов + календарь ─► проверка ─► УТВЕРЖДЕНИЕ КАРКАСА
        ─► content (тексты, рабочая программа, лекции, семинары, тесты, аттестация, литература, слайды)
        ─► проверка V01–V46 + добор недостающего + смысловая проверка ─► комплект и отчёт
```

- `app/models.py` — модель комплекта, единственный источник правды; у каждого объекта стабильный ID
  (`M2` модуль, `T2.3` тема, `LO1.2` результат обучения, `Q17` вопрос), связи только через ID.
- `app/pipeline/` — шаги агента и оркестратор (состояния сессии, параллельные вызовы, бюджет).
- `app/core/` — детерминированное ядро: солвер часов, календарь, проверки, реестр, библиография.
- `app/llm.py` — клиент шлюза: ответы по JSON-схеме, повторы, кеш, учёт расходов, предохранитель.
- `app/api/` — HTTP API (FastAPI), `app/storage/` — сессии на диске.

Подробно — `docs/ARCHITECTURE.md`. Правила шаблонов — `docs/templates_spec_pk.md` и `docs/templates_spec_dop.md`,
список проверок — `docs/checks_matrix.md`.

## Навыки агента

Каждый шаг, где работает модель, — отдельный навык: файл `app/skills/<шаг>.md` с ролью, правилами, схемой ответа
и параметрами вызова. Навыки: `intake`, `clarify`, `skeleton`, `program_texts`, `module_content`, `lectures`,
`seminars`, `tests`, `final_attestation`, `literature`, `module_pack` (экономный режим), `judge` (смысловая
проверка). Поведение агента меняется правкой навыка, без изменения кода.

## Тесты

```bash
.venv/bin/python -m pytest -q        # все тесты в режиме mock, без сети и расходов
.venv/bin/python scripts/smoke.py    # сквозная проверка API на одном запросе, без запуска сервера
```

Тесты всегда идут в режиме mock, даже если ключи шлюза заданы. Тесты с настоящей моделью помечены маркером
`llm` и запускаются только явно: `.venv/bin/python -m pytest -m llm` (тратит деньги).
